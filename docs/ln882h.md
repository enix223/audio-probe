# LN882H + GX8006 Platform Notes

This document covers the first embedded target: **LN882H** (Liangniu Wi-Fi MCU)
with a **GX8006** voice co-processor. It records what is known, what is assumed,
and what must be verified before the recorder advertises a capability.

Status: design/bring-up plan. No LN882H firmware exists yet.

---

## 1. Hardware topology

```
                 MQTT broker / IoT cloud (control)
                          ▲
                          │ Wi-Fi
┌──────────────┐          │            ┌────────────────────┐
│ LN882H       │──────────┴───────────►│ WS analysis server │
│ recorder core│      Wi-Fi / WS        └────────────────────┘
│  MQTT ctrl   │
│  UART1 1Mbps │──────── GX8006 ── I2S ── Mic
│              │            └────────────── Speaker / PA
└──────────────┘
   debug UART, flash, GPIO flow control
```

- LN882H runs the recorder core, Wi-Fi, MQTT control, WebSocket data plane,
  segmenter/telemetry, and the GX8006 protocol.
- GX8006 owns the mic ADC, speaker DAC, and its own VAD. It sends mic data to
  LN882H over UART. **KWS/wake word is disabled**: capture starts on an MQTT
  `start` command, not a wake word.
- A GPIO flow-control line (GX8006 → LN882H) indicates the chip is ready to
  receive speaker data. It is used for the speaker/test-tone path, not for
  control commands.

Reference implementation: ai-voice
`src/platforms/ln882h/{protocol,audio,ws,factory}` and
`docs/ln882h.md`. The recorder must not compile the existing voice-coupled
`HalAudioGx8006` unchanged; see §5.

### 1.1 Control plane

- MQTT is always connected and controls start/stop; see
  [`mqtt-control.md`](mqtt-control.md). There is no wake word.
- Reuse embedded-iot-client's `AppInit`/`IoTCore`/`ThingModelContext` like
  ai-voice. Register the internal `recorderCmd` datapoint; report
  `recorderStatus`.
- WebSocket connects on demand when MQTT `start` arrives and may close after
  stop (`ws_mode=on_demand`). This is important for LN882H RAM.
- The GX8006 mic is opened by the recorder when capture starts. Do not arm KWS
  or wait for a wake event.

## 2. Critical uncertainty: PCM vs Opus

The GX8006 SmartBot protocol enum includes PCM, Speex, Opus, and MP3. ai-voice's
handshake can be compiled to request PCM (`CONFIG_AI_BAIDURTC_AUDIO_CODEC_RAW`),
**but**:

- ai-voice's documentation describes the mic path as Opus.
- `HalAudioGx8006::Read()` documents "The GX8006 sends Opus frames, not raw
  PCM" and reinterprets bytes as `int16_t`.
- ai-voice's shipping voice path uses chip Opus and does not validate PCM mic
  output.
- The PCM enum is known to work for the **speaker** path; mic PCM is unproven.

**Decision for the first milestone:** the LN882H recorder advertises **Opus-only
capture**. Do not advertise `pcm_s16le` until a bench test proves the chip
returns PCM `GET_MIC_DATA` with the expected sample format/lengths.

### 2.1 Bench test to resolve it

1. Configure `SET_MIC_CONFIG` with `format = PCM`, 16 kHz, 16-bit, mono.
2. Enable mic upload (see §4.4) and capture raw `GET_MIC_DATA` payloads.
3. Check:
   - Are payload lengths consistent with PCM (e.g. ~320 B for 10 ms,
     ~640 B for 20 ms) or Opus (variable, small)?
   - Does a known sine/speech decode correctly as PCM, or is it noise unless
     Opus-decoded?
   - Does the chip accept odd-length payloads? (PCM frames are even; Opus may
     not be.)
   - Does the format change affect the speaker path independently?
4. Record the result in `provenance`/`docs/ln882h.md` and only then enable the
   capability.

If PCM is proven:
- Advertise `pcm_s16le`, 16 kHz mono, with a measured max frame size (around
  640 B for 20 ms; never assume 256 B).
- Enable device energy VAD + pre-roll.
- Re-run the quality metrics on raw PCM.

If Opus-only:
- Advertise `opus`, `encoders: ["gx8006"]`, and `vad: ["server","device"]`.
- Stream continuous Opus; server performs VAD, pre-roll, and segmentation.
- Device `device_pre_roll_max_ms: 0`; no device PCM stats (`STATS_VALID`
  clear).

## 3. UART and GX8006 protocol

### 3.1 UART

| Parameter | Value |
|---|---|
| Port | UART1 on LN882H |
| TX/RX | GPIOA_PIN_2 / GPIOA_PIN_3 (verify against the board) |
| Flow control | GPIOA_PIN_5, HIGH = GX8006 ready (verify) |
| Baud | 1,000,000, 8N1 |
| DMA | Enable UART1 DMA; RX buffer ≥2048 bytes |
| RX handling | DMA circular/IDLE + half/full callbacks; feed a frame parser |
| TX | Serialized by one writer; control commands and speaker data share the port |

`CONFIG_IOT_UART_DMA_ENABLE=1` and a sufficiently large
`CONFIG_IOT_UART_DMA_RX_BUF_SIZE` are required for PCM-sized bursts. The ai-voice
generated config leaves DMA off in some builds; do not copy that for the
recorder.

### 3.2 SmartBot frame

```
+--------+---------+------+--------+-----------+----------+
| Head   | Version | Cmd  | Length |  Payload  | Checksum |
| 2B     | 1B      | 1B   | 2B BE  |  N bytes  | 1B       |
+--------+---------+------+--------+-----------+----------+
```

- Head `0xAA55`, version `0x00` (request) / `0x03` (response), cmd `0x92`.
- Length is big-endian; checksum is the byte sum mod 256.
- Multi-byte payload fields are big-endian.
- Max frame is chip-dependent; ai-voice uses 660 bytes on the wire. The
  recorder's mic queue must accept measured PCM frames up to at least 768 bytes
  unless the chip proves a smaller limit.

Relevant subcommands:

| Sub-command | Direction | Use |
|---|---|---|
| `0x01 VERSION_QUERY` | LN → GX | Handshake |
| `0x02 SET_MIC_CONFIG` | LN → GX | Rate/bits/channels/gain/format/max recv |
| `0x03 SET_SPK_CONFIG` | LN → GX | Rate/bits/volume/format/max send |
| `0x05 GET_MIC_DATA` | GX → LN | START/MID/STOP + audio payload |
| `0x06 SET_SPK_DATA` | LN → GX | START/MID/STOP + audio payload |
| `0x07 SET_OFFLINE_CONFIG` | LN → GX | Mic on/off, VAD, pickup period, wake notify |
| `0x08 GET_OFFLINE_WAKEUP` | GX → LN | Wake event |
| `0x09 GET_TIME_OUT` | GX → LN | Session timeout |
| `0x0F/0x12 EVENT_NOTIFY` | GX → LN | Speaker playback status |

Audio format enum: PCM=0, Speex=1, Opus=2, MP3=3.

### 3.3 Handshake

```
LN882H                              GX8006
  |-- VERSION_QUERY ----------------->|
  |<-- VERSION_RESP ------------------|
  |-- VERSION_CONFIRM --------------->|
  |-- SET_MIC_CONFIG ---------------->|   rate/bits/ch/gain/format
  |<-- MIC_CONFIG_RESP ---------------|
  |-- SET_SPK_CONFIG ---------------->|   rate/bits/volume/format
  |<-- SPK_CONFIG_RESP ---------------|
  |   [Ready]                         |
```

The recorder must send the mic format it will actually use and record the
response. It must not assume that setting `PCM` succeeded; verify on the first
mic payload.

### 3.4 Mic data flow and continuous pickup

Normal chip-VAD flow:

1. GX8006 sends `GET_MIC_DATA START`.
2. N × `GET_MIC_DATA MID` with audio payload.
3. `GET_MIC_DATA STOP`.

Continuous-pickup flow:

- `SET_OFFLINE_CONFIG MIC = 1` (mic on).
- `SET_OFFLINE_CONFIG VAD = 0` (disable chip VAD) to request continuous upload.
- Keep KWS/wake-word offline wakeup disabled; do not arm a wake word. Capture
  starts on the MQTT `start` command, not on a chip wake event.
- Configure the pickup period (`SET_OFFLINE_CONFIG PICKUP_PERIOD`), and
  re-arm with `WAKE_NOTIFY` after a session ends or a speaker abort. Here
  `WAKE_NOTIFY` is a chip session re-arm command, not a wake-word detector.
- The vendor's 60-second pickup window and behavior after it expires are
  **unverified**. Soak-test and re-arm periodically if needed.
- Even in continuous mode, the chip may emit one START/MID…STOP session. Treat
  START/STOP as informational source events in server-VAD mode.

If continuous mode is not reliable:
- Use chip-VAD segments (`vad.engine: device`) with no controlled pre-roll.
- The server can still analyze level/SNR but cannot recover audio before the
  chip's START.

### 3.5 Speaker / test tone

- The chip's speaker path accepts Opus natively and may accept PCM depending on
  `SET_SPK_CONFIG`.
- Test-tone PCM chunk size is unverified. Start with small chunks (e.g.
  240 bytes) and respect flow control; validate on the bench before advertising
  `test_tone`.
- The existing ai-voice speaker queue (`Gx8006SpkQueue`) is frame-preserving and
  is a useful reference. A single feeder task must own START/STOP and packet
  counters; never interleave them from multiple tasks.
- If PCM speaker output is unreliable, encode the test tone to Opus and send it
  through the Opus speaker path, or omit the test-tone capability on LN882H
  until validated.

## 4. Recorder integration

### 4.1 Gx8006AudioSource (recorder-specific fork)

Do not compile `HalAudioGx8006` unchanged. Implement:

- UART open/close, RX task, protocol parser.
- A frame-preserving queue of mic packets with exact byte lengths.
- `Read()` returns one packet at a time; it must never truncate or reinterpret
  bytes as `int16_t` for Opus.
- Queue slot size ≥ measured max (initial target 768 bytes; adjust after
  bring-up).
- Source events for START/STOP, chip reboot, UART overflow, queue drop.
- `ReadBytes()`-style API; PCM and Opus share the same byte queue.
- Re-handshake after a chip reboot; re-arm mic/upload/pickup.
- Counters exposed to telemetry: UART overruns, queue drops, truncations
  (must be zero), chip reboots, parse errors.

### 4.2 Segmenter behavior

- Opus-only first milestone: pass frames through; no local VAD/pre-roll. The
  server VAD handles utterances. The device emits capture/file-block segments.
- Chip-VAD fallback: use START/STOP as segment boundaries; pre-roll is 0.
- If PCM is proven: use the shared energy VAD + pre-roll path, with the
  pre-roll ring sized from measured frame duration.

### 4.3 Header telemetry

- Opus chip packets: `STATS_VALID` clear, RMS/peak/DC sentinels, `vad_score`
  255 (or chip VAD 0/100), `samples` from TOC.
- PCM: compute RMS/peak/DC/clip on the device.
- The server always recomputes from decoded/raw PCM.

### 4.4 TX queue and backpressure

- Frame-preserving queue; control records are never dropped while the link is
  alive.
- Audio drops are oldest-first; count them and mark the next frame
  DISCONTINUITY.
- With Opus at ~16 kHz mono 20 ms, the queue can be small (16 KB is a reasonable
  starting point). With PCM, budget for `tx_queue_ms` at 32 KB/s.
- Never block the UART RX task or the capture path on the socket.

## 5. Memory and threading

### 5.1 RAM budget (295 KB total)

MQTT is always on; WebSocket is on demand. MQTT TLS + HTTP/thing model (when
the backend needs it) are resident, and WS TLS is resident only while
recording. Budget items:

| Item | Approx |
|---|---|
| mbedTLS MQTT TLS | 35–40 KB |
| mbedTLS WS/WSS TLS (while recording) | 35–40 KB |
| lwIP pools/buffers | 10–20 KB |
| HTTP/thing-model buffers (if used) | 4–12 KB |
| WS RX/TX buffers | 2–4 KB |
| UART DMA RX | ≥2 KB |
| GX8006 mic queue | 4–8 KB (measure) |
| TX queue | 8–16 KB |
| Stacks (see below) | 20–30 KB |
| App/scheduler/event/network | 20–30 KB |
| Heap headroom | keep ≥20 KB for reconnect |

If both TLS connections do not fit reliably:
- use `ws_mode=on_demand` (default) and free WS TLS after stop;
- bring up with MQTT TLS + `ws://` on a trusted lab LAN, then measure WSS;
- keep the mbedTLS input buffer at its known-good 16 KB until the Go server's
  TLS record behavior is tested;
- never silently disable certificate verification in production.

Measure free heap and stack high-water marks; do not assume. A low-heap reboot
guard from embedded-iot-client is useful, but a recorder should log the minimum
before rebooting.

### 5.2 Threads/stacks

| Task | Initial stack | Notes |
|---|---:|---|
| `ws_recv` | 4096 | mbedTLS read |
| `ws_tx` | 3072 | blocking send |
| `gx8006_rx` | 4096 | UART parse/queue |
| `gx8006_spk` | 3072 | flow control + speaker |
| recorder app | 6144 | capture/segment/commands |
| event/network/system | embedded-iot-client defaults | measure |

Use UART DMA and a short RX poll interval; do not spin-wait in the app task.

### 5.3 Shutdown order

Stop capture → close segment → stop TX → close WebSocket → stop GX tasks →
stop audio → stop scheduler.

## 6. Wi-Fi, MQTT, and security

- First milestone: compile-time Wi-Fi **and MQTT** credentials in a
  **gitignored generated header** (`platform_config.h` template in the repo).
  This includes the broker endpoint/port, product/device id, device secret, and
  MQTT CA if TLS is used.
- `CONFIG_IOT_NETWORK_SSID/PASSWORD` take priority over stored credentials in
  embedded-iot-client's `ConfigStore`.
- BLE provisioning is optional. With MQTT required, the built-in
  embedded-iot-client provisioner (which completes on MQTT connect) is a
  natural fit; it remains disabled in the first compile-time-credential
  milestone to save RAM.
- MQTT TLS with CA verification where the backend supports it. If the lab
  broker is plaintext, make it an explicit develop-only configuration and
  document it.
- `wss://` with CA verification by default. ai-voice's LN882H WS client
  currently disables certificate verification; patch it before shipping. Apply
  the same rule to MQTT.
- Provide an explicit develop-only option for `ws://` (LAN bring-up), e.g. a
  compile-time macro and a startup warning.
- Never commit credentials, tokens, or CA private material.
- There is **no wake word/KWS**; capture is started by MQTT. Do not enable
  GX8006 offline KWS or an ESP-SR wake-word model.

## 7. Build and flash

### 7.1 Setup

`build/ln882h/setup.sh` mirrors ai-voice's flow:

1. Copy `project/recorder` into `$LN882H_SDK/project/recorder`.
2. Substitute absolute paths for the recorder and vendored sources.
3. Copy `proj_config.h`, partition table/config, and linker script.
4. Set `USER_PROJECT=recorder` in the SDK root CMake (or print instructions).
5. Create `src/platform/ln882h/config/platform_config.h` from the template if
   absent (SSID/password/server URL/token).

### 7.2 Source lists

Explicitly list (no globbing):

- SDK: startup, Wi-Fi, lwIP, DHCP, mbedTLS, partition manager, FreeRTOS glue,
  MQTT (coreMQTT or the SDK's MQTT client).
- embedded-iot-client: storage/flash bridge, network, system, threading,
  serial/log, cfgstore, eventbus, scheduler, MQTT client, `IoTCore`,
  `ThingModelContext`, command handler, NTP, HTTP as needed for the thing model.
- Vendored ai-voice: GX8006 protocol, speaker queue, WS transport.
- Recorder core + `main.c`/`cl_recorder_platform_ln882h`.

MQTT/IoT core and thing model are **required** for control. Do not compile BLE
provisioning or OTA in the first milestone unless needed. Link only the required
SDK libraries.

### 7.3 Commands

```
make ln882h-recorder-setup
make ln882h-recorder-build
make ln882h-recorder-flash
make ln882h-recorder-monitor
```

The exact SDK/toolchain paths come from `.env`/environment, as in ai-voice.

## 8. Diagnostics and telemetry

Expose in `telemetry`/`stats`:

- Free heap, minimum free heap, stack high-water marks.
- UART RX overruns, DMA errors, parse errors.
- Mic queue drops/truncations (truncation must be zero).
- Chip reboots/re-handshakes, START/STOP counts, session duration.
- TX queue high-water/drops, send errors, reconnects.
- MQTT connection state, command id/action, status publish failures, and
  MQTT-loss events.
- WS state (`idle`, `connecting`, `handshaking`, `capturing`, `draining`) and
  `ws_mode`/idle-timeout behavior.
- Wi-Fi RSSI (if the SDK exposes it).
- Watchdog resets (persist a boot counter).

The server report should flag LN882H captures as chip-Opus when applicable and
note whether device VAD was used.

## 9. Known limitations and follow-ups

- **PCM vs Opus**: unresolved until bench test; first milestone is Opus-only.
- **Continuous pickup**: 60 s window/behavior unverified; soak and re-arm.
- **UART throughput**: 1 Mbps is sufficient for 16 kHz mono PCM/Opus, but DMA
  and buffering must be validated; large PCM bursts are the risk.
- **TLS memory**: MQTT TLS is always on; WS/WSS TLS may coexist while recording.
  Both plus lwIP may leave little reconnect headroom. Use `ws_mode=on_demand`,
  measure, and tune lwIP/mbedTLS only with evidence.
- **MQTT control**: requires a broker/thing model and credentials; the
  recorderCmd/recorderStatus properties must exist or the compile-time fallback
  model must be configured. Test duplicate/expired commands and MQTT loss.
- **No wake word**: capture starts on MQTT. Do not enable GX8006 KWS or an
  ESP-SR wake-word model; `WAKE_NOTIFY` is only a chip session re-arm.
- **Speaker/test tone**: PCM chunk limits and loopback path unverified.
- **BLE provisioning**: optional/deferred; compile-time credentials first.
- **Firmware recovery**: retain the vendor boot/Wi-Fi/lwIP startup sequence; do
  not replace it with a generic scheduler.
- **Chip re-handshake**: reapply mic/speaker config after a reported reboot.

## 10. Acceptance checklist

- [ ] UART1 DMA at 1 Mbps; RX ≥2048; flow-control pin verified.
- [ ] Handshake stable across 100 resets; chip version/response logged.
- [ ] Bench test proves whether mic output is PCM or Opus; capability matrix
      updated honestly.
- [ ] Continuous pickup (or chip VAD fallback) works for ≥10 minutes without
      dead air; re-arm behavior documented.
- [ ] Mic frames preserve exact lengths, including odd Opus packets; no
      truncation; max frame measured.
- [ ] MQTT connects; `recorderCmd` start opens WS and begins capture; `stop`
      finalizes the segment; status is published on connect/state changes.
- [ ] Duplicate `id` does not double-start; expired command is rejected; MQTT
      loss stops capture after the configured timeout.
- [ ] WS `start_capture`/`stop_capture` is nacked while MQTT owns control.
- [ ] No KWS/wake-word engine is initialized; capture starts only on MQTT.
- [ ] WSS with CA verification connects and reconnects after AP/server restarts;
      MQTT TLS/CA behavior is documented.
- [ ] Heap/stack high-water marks and reconnect headroom measured for
      MQTT-only idle and MQTT+WS recording.
- [ ] No watchdog resets during a 10-minute soak.
- [ ] Server receives hello/telemetry/audio; decoded WAVs are valid.
- [ ] Test tone validated or capability omitted.
- [ ] Credentials are not in the repository.
